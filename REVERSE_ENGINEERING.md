# Reverse-engineering notes

Input: user-supplied `mattmoss.scr`, PE32 x86 Windows GUI executable, version 1.0.0.1, embedded attribution 1996 HyperDyne Pty Ltd Australia. Static analysis used PE headers, resources, strings and x86 disassembly. The full Windows program was not executed.

## Recovered routines

| Original virtual address | Function |
|---|---|
| `0x401000` | Random coordinate pair |
| `0x401033` | Screensaver window procedure / timer handling |
| `0x4014fe` | 236-entry intensity lookup |
| `0x401661` | Generate RGB palette using intensity and phase |
| `0x401730` | Interpolate base colour and advance palette phase |
| `0x401e80` | Generate randomly positioned, nonzero weighted source points |
| `0x40222c` | Calculate field magnitude |
| `0x40233f` | Shuffled 48 × 36 drawing traversal, alternating scanlines |
| `0x4030e0` | Microsoft C pseudo-random generator |

For each source `(px, py, weight)`, at pixel `(x, y)`:

```text
dx = px - x
dy = py - y
distance2 = dx*dx + dy*dy
half = trunc((dx*dy)/2)
u += trunc((weight*dx*half)/distance2)
v += trunc((weight*dy*half)/distance2)
value = trunc(sqrt(u*u + v*v)) & 65535
index = (value / band_divisor) % 236
```

The products and sums use signed 32-bit wrapping arithmetic; replacing this with unbounded arithmetic changes the image. Division truncates toward zero. At an exact source position, the original returns the previously computed field value. The port does the same. The square-root tail's negative-overflow case maps to a zero low word; the original CRT error path was not independently emulated.

The original lookup uses `trunc(16384 - sin(i * 3.14 / 235) * 16384)`, with literal **3.14**. It also contains a parabolic alternative. The only observed call to rebuild this table is initialization, so the running port retains its initial sine lookup even though the window procedure later toggles the selection flag.

The initial scene has 4 sources and band divisor 1. Later scenes have 3–10 sources and divisors 2–4. Weights are in −4…4 excluding zero. The base RGB colour interpolates towards another random colour over 236, 472, 708 or 944 palette steps. Each display pixel holds an index into a 236-colour palette.

## What is preserved

- Core field integer arithmetic and 16-bit result.
- Microsoft C PRNG recurrence `state = state * 214013 + 2531011`, output `(state >> 16) & 32767`.
- Source generation ranges, palette intensity, colour interpolation and palette phase.
- Original shuffled scatter traversal; alternating-row retention is available as an opt-in mode.

## Version 0.1.2 smooth desktop presentation

The desktop uses `SmoothAnimation` with a default speed of 0.25×. Complete fields are prepared before display, palette steps are fractionally interpolated, startup fades from black, and scene changes use a smoothstep crossfade. Fade duration is one simulation second (four seconds at the default). These are deliberate modern additions; the integer field and optional historical renderer are retained. See README.md for the maths.

## Version 0.1.1 correction

The first desktop release enabled historical interlacing by default, producing visible scanline/comb artifacts and mixing alternate rows of unrelated patterns. The corrected default renders every row and uses linear scaling. Press I or pass `--interlace` to restore the historical appearance. The field formula and palette are unchanged.

## Intentional adaptations and limits

- Fixed 640 × 480 virtual canvas; original used the current client rectangle. This also keeps traversal within the recovered permutation table bounds.
- Portable RGBA texture rendering replaces GDI and hardware palette support. The original only animated palettes on supported display devices; modern output always animates.
- A session seed replaces two timing-dependent GetTickCount reseeds. Same seed reproduces this port, not an identical historical machine's random sequence.
- In the optional historical mode, scatter drawing is paced at 720 passes/second; the original was CPU/GDI limited. Idle palette animation follows the original requested 10 ms timer, though actual Windows 95/NT timer resolution could differ.
- Floating-point sine and square root use the host Rust implementation; no promise of x87 bit-identical floating-point results across all CPUs.
- Source ownership and original copyright are not changed by this reconstruction.
- No full, side-by-side visual comparison with the original running under Windows has been performed.

## Reference tests

The 1,000 cases in `original_x86.rs` were generated by loading the original instruction bytes at `0x40222c` into Unicorn's x86 emulator. They cover 3–10 weighted sources and pixels throughout 640 × 480, with exact-source cases every 50 samples. The integer instruction sequence executes unchanged. At `0x40230a`, Python's square root and truncation supply the floating-point tail result, then execution resumes at `0x402320`. Thus these cases independently verify the difficult integer arithmetic but do not validate the original CRT square-root implementation.
